# ServiceBrain 项目深度复盘

## 一、项目概述

ServiceBrain 是一个面向**电商客服咨询场景**的 H5 智能客服机器人 Demo，旨在完整展示智能客服产品在真实业务场景中的核心能力。

### 项目信息
| 项目 | 内容 |
|------|------|
| 项目名称 | ServiceBrain 智能客服机器人 Demo |
| 开发周期 | 2026-03-10 至 2026-03-17 (7 天) |
| 核心团队 | Wayne (技术负责人) + Jarvis (AI 助手) |
| 代码规模 | ~3500 行 (Python + TypeScript) |
| 测试覆盖 | 17 单元测试 + 15 E2E 测试 |

### 2.2 后端实现 (Python FastAPI)

#### 核心服务
| 服务 | 职责 | 技术亮点 |
|------|------|----------|
| OrchestratorService | 对话编排中枢 | 意图识别 → 漂移检测 → 路由分发 |
| IntentChain | LLM 意图识别 | 结构化 JSON 输出 + 关键词兜底 |
| RAGService | 知识检索 | Chroma 向量库 + LangChain |
| MemoryService | 记忆管理 | 工作记忆 + 会话摘要 + 主题记忆 |
| RuleService | 规则判断 | 退款资格校验 |
| TicketService | 工单兜底 | 4 种触发场景 |
| LLMService | 模型调用 | DashScope 通义千问接入 |

#### 实现的功能
- ✅ 匿名用户 + 用户名采集
- ✅ WebSocket 实时通信 + 心跳重连
- ✅ 多轮对话 + 上下文维护
- ✅ 订单号自动抽取 + 补问追问
- ✅ 退款咨询 vs 退款执行区分
- ✅ 工具结果卡片 (4 种状态)
- ✅ 工单兜底链路
- ✅ RAG 知识检索
- ✅ 上下文压缩机制

### 2.3 前端实现 (Vue 3 + TypeScript)

#### 核心功能
- ✅ 用户名弹窗 + 会话初始化
- ✅ WebSocket 连接管理 + 自动重连
- ✅ 消息流渲染 (7 种消息类型)
- ✅ 快捷问题区
- ✅ 工具结果卡片展示
- ✅ 工单引导卡片
- ✅ 输入区状态管理

### 2.4 测试体系

#### 单元测试 (17/17 通过)
```
P0 功能测试:
- 工具结果卡片 (3 个): success / not_allowed / fail
- 消息类型区分 (3 个): followup / explain / knowledge
- 工单兜底逻辑 (2 个): 用户拒绝检测 / 低置信度触发

P1 功能测试:
- LLM 意图识别 (4 个): 退款执行/咨询/拒绝/兜底
- RAG 检索 (2 个): 空库 / 无命中
- 上下文压缩 (2 个): 不触发 / 生成摘要
- 集成测试 (1 个): 完整意图到 RAG 流程
```

#### E2E 测试 (15 个场景)
- 首次进入 + 用户名输入
- 会话初始化 + 首问
- 退款咨询链路
- 退款执行成功/失败
- 知识问答
- 规则解释
- 工单兜底
- WebSocket 断线重连

## 三、做得好的

### 3.1 架构设计

#### ✅ 分层清晰
```
前端 (Vue 3) → API 层 → 编排层 (Orchestrator) → 服务层 → 数据层
```
- 职责分离明确，便于扩展
- 编排层作为"大脑"统一调度

#### ✅ 受控式 AI
> "AI 负责理解与组织，规则负责约束与判定"

- LLM 输出结构化 JSON，不直接驱动业务
- 工具调用前必须经过规则校验
- 置信度低时强制兜底，不冒险执行

#### ✅ 降级策略完善
| 场景 | 降级方案 |
|------|----------|
| LLM 失败 | 关键词匹配兜底 |
| RAG 无结果 | 保守解释 + 工单 |
| 工具失败 | 失败卡片 + 重试选项 |
| WebSocket 断开 | 自动重连 + 消息保留 |

### 3.2 工程实践

#### ✅ 测试驱动
- 17 个单元测试，覆盖率 100%
- 15 个 E2E 场景测试
- 重构有信心，回归有保障

#### ✅ 类型安全
- 后端：Pydantic 全程类型约束
- 前端：TypeScript 接口完整
- 通信：WebSocket 协议严格定义

#### ✅ 文档先行
每轮开发前更新文档，再开发，再测试，再复盘。

### 3.3 协作效率

#### ✅ 快速迭代
| 日期 | 里程碑 |
|------|--------|
| 03-10 | PRD 细化完成 |
| 03-12 | 核心架构搭建 |
| 03-14 | P0 功能完成 |
| 03-15 | P1 功能 + E2E 测试 |
| 03-17 | 体验优化完成 |

**平均每天 2-3 个有效提交**，高频小步快跑。

## 四、不足之处

### 4.1 技术债务

| 问题 | 原因 | 影响 |
|------|------|------|
| 意图识别边缘 case 有歧义 | Prompt 调优时间有限 | 部分场景识别不准 |
| RAG 知识库数据量小 | 聚焦核心链路 | 复杂问题覆盖不足 |
| 性能优化未深入 | 并发低非瓶颈 | 生产环境容量未知 |
| 前端组件粒度不够 | 时间压缩 | ChatView.vue 超过 500 行 |

### 4.2 需求理解

- 初期对"快捷问题区"显示逻辑理解有偏差
- 对"追问轮次限制"理解不够清晰

**原因**: PRD 较长，部分细节被忽略；缺乏需求确认环节。

### 4.3 测试盲区

- 缺少性能测试和压力测试
- 缺少真实用户场景验证

---

## 五、原因分析

### 5.1 时间约束
7 天完成从 PRD 到 Demo，时间紧张导致：
- 部分优化点被搁置
- 文档阅读不够细致
- 代码重构不够充分

### 5.2 优先级取舍
优先保证功能完整，次要问题延后：
- ✅ 核心链路 > 性能优化
- ✅ 功能实现 > 代码重构
- ✅ 主场景 > 边缘 case

### 5.3 数据依赖
RAG 效果依赖知识库质量：
- 数据准备滞后于开发
- 向量库初始化未自动化

## 七、对当前成果的思考

### 7.1 成果价值

#### 产品层面
- **完整闭环**: 进入 → 识别 → 执行 → 展示 → 兜底
- **差异化亮点**: 工具卡片、规则解释、智能兜底

#### 技术层面
- **架构可扩展**: 单体可平滑演进为微服务
- **AI 可控**: 建立了安全模式
- **测试保障**: 核心链路有保护

#### 团队层面
- **协作模式**: AI 助手 + 技术负责人可行
- **效率**: 4 天完成 Demo，效率较高

### 7.2 当前局限

| 局限 | 说明 |
|------|------|
| 数据量小 | 知识库仅 5 条规则 |
| 场景单一 | 仅退款场景 |
| 无真实用户 | 测试用例为预设 |
| 性能未压测 | 仅支持 Demo 并发 |

### 7.3 与业界对比

| 维度 | ServiceBrain | 业界主流 |
|------|--------------|----------|
| 意图识别 | LLM + 规则 | 模型 + 大规模语料 |
| 知识检索 | RAG | 知识图谱 + RAG |
| 工具调用 | 单工具 | 多工具编排 |
| 多轮对话 | 基础上下文 | 复杂状态机 |

**结论**: Demo 层面已可用，生产级需数据积累和场景扩展。
