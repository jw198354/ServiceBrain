## 二、做得好的地方

### 2.1 架构设计层面

#### ✅ 分层架构清晰
```
┌─────────────────────────────────────┐
│  H5 Vue 前端 (Presentation)          │
├─────────────────────────────────────┤
│  WebSocket / HTTP 接入层             │
├─────────────────────────────────────┤
│  编排服务 (Orchestrator)             │
│  - 意图识别 → 漂移检测 → 路由分发     │
├─────────────────────────────────────┤
│  服务层                              │
│  - LLMService / RAGService          │
│  - MemoryService / RuleService      │
│  - TicketService / ToolService      │
├─────────────────────────────────────┤
│  数据层 (SQLite + Chroma)            │
└─────────────────────────────────────┘
```

**为什么好：**
- 职责分离明确，便于后续扩展
- 编排层作为"大脑"统一调度，避免服务间循环依赖
- 记忆服务独立封装，支持工作记忆/会话摘要/主题记忆三层

#### ✅ 受控式 AI 设计
> "AI 负责理解与组织，规则负责约束与判定"

**具体实践：**
- LLM 输出结构化 JSON，不直接驱动业务动作
- 退款工具调用前必须经过 `RuleService` 资格校验
- 意图置信度低于 0.3 时强制进入兜底，不冒险执行

**价值：** 在 Demo 阶段就建立了安全边界，避免"AI 幻觉导致误操作"的风险。

#### ✅ 降级策略完善
| 场景 | 降级方案 |
|------|----------|
| LLM 调用失败 | 自动降级到关键词匹配意图识别 |
| RAG 检索无结果 | 保守解释 + 工单引导 |
| 工具调用失败 | 失败卡片 + 重试/工单选项 |
| WebSocket 断开 | 自动重连 + 消息队列保留 |

## 三、不足之处与原因分析

### 3.1 技术债务

#### ⚠️ 意图识别仍有优化空间
**问题：**
- 虽然实现了 LLM 意图识别，但部分边缘 case 仍有歧义
- "我要退款" vs "我想了解退款" 的区分依赖模型能力

**原因：**
- Prompt 工程时间有限，未能充分调优
- 缺乏真实用户数据做 few-shot 示例

**改进方向：**
- 增加意图分类的 few-shot 示例
- 引入意图置信度校准机制
- 建立意图识别错误日志，持续优化

#### ⚠️ RAG 知识库数据量小
**问题：**
- 当前仅内置 5 条规则文档
- 复杂问题的检索召回率未经验证

**原因：**
- Demo 阶段聚焦核心链路，数据准备优先级较低
- 向量库初始化流程尚未自动化

**改进方向：**
- 提供知识库批量导入脚本
- 建立知识库效果评估机制
- 支持多格式文档解析（PDF/Word/Markdown）

#### ⚠️ 性能优化未深入
**问题：**
- LLM 调用延迟未做缓存优化
- 长对话的上下文压缩策略较简单

**原因：**
- Demo 场景并发低，性能不是瓶颈
- 时间有限，优先保证功能完整

**改进方向：**
- 引入 Redis 缓存常见意图识别结果
- 优化上下文压缩算法（语义摘要 vs 简单截断）
- 添加 LLM 调用超时和重试机制

### 3.2 工程实践

#### ⚠️ 部分代码重复
**问题：**
- 卡片生成逻辑在 orchestrator 中分散
- 错误处理模式有重复代码

**原因：**
- 快速迭代中追求先跑通，后重构
- 部分抽象在需求明确后才清晰

**改进方向：**
- 提取卡片生成器工厂模式
- 统一错误处理装饰器

#### ⚠️ 前端组件粒度不够细
**问题：**
- ChatView.vue 超过 500 行，职责较重
- 消息渲染逻辑集中，扩展新消息类型成本较高

**原因：**
- 前端开发时间压缩，优先保证功能
- 组件拆分需要更多设计时间

**改进方向：**
- 拆分为 MessageList / MessageItem / InputArea 等独立组件
- 消息类型使用策略模式渲染

### 3.3 协作过程

#### ⚠️ 需求理解有偏差
**问题：**
- 初期对"快捷问题区"的显示逻辑理解有误
- 对"追问"的轮次限制理解不够清晰

**原因：**
- PRD 文档较长，部分细节在快速阅读中被忽略
- 缺乏需求确认环节（如需求评审会）

**改进方向：**
- 建立需求 Checklist，逐项确认
- 关键交互逻辑用流程图确认后再开发

#### ⚠️ 测试覆盖有盲区
**问题：**
- E2E 测试依赖 Playwright，但环境配置复杂
- 缺少性能测试和压力测试

**原因：**
- 时间有限，优先保证功能测试
- Demo 阶段未要求性能指标

**改进方向：**
- 补充性能基准测试
- 添加并发会话测试

## 五、对当前阶段成果的思考

### 5.1 成果价值

#### 产品层面
1. **完整闭环**：从用户进入 → 意图识别 → 工具执行 → 结果展示 → 工单兜底，全链路打通
2. **差异化亮点**：
   - 工具结果卡片（可视化执行结果）
   - 规则解释能力（不只是 FAQ）
   - 智能兜底（不是简单"转人工"）

#### 技术层面
1. **架构可扩展**：当前单体架构可平滑演进为微服务
2. **AI 可控**：建立了"模型理解 + 规则约束"的安全模式
3. **测试保障**：17 个单元测试 + 15 个 E2E 测试，核心链路有保护

#### 团队层面
1. **协作模式验证**：AI 助手 + 技术负责人的协作模式可行
2. **效率提升**：4 天完成从 PRD 到可演示 Demo，效率较高

### 5.2 当前局限

| 局限 | 说明 | 影响 |
|------|------|------|
| 数据量小 | 知识库仅 5 条规则 | 复杂问题覆盖不足 |
| 场景单一 | 仅退款场景 | 其他售后场景未覆盖 |
| 无真实用户 | 测试用例为预设 | 真实场景表现待验证 |
| 性能未压测 | 仅支持 Demo 并发 | 生产环境容量未知 |

### 5.3 与业界对比

| 维度 | ServiceBrain | 业界主流 (如阿里小蜜) |
|------|--------------|---------------------|
| 意图识别 | LLM + 规则 | 模型 + 大规模语料训练 |
| 知识检索 | RAG (向量检索) | 结构化知识图谱 + RAG |
| 工具调用 | 单工具 Demo | 多工具编排 + 工作流 |
| 多轮对话 | 基础上下文 | 复杂状态机 + 槽位管理 |
| 兜底能力 | 工单引导 | 人工无缝接管 |

**结论**：ServiceBrain 在 Demo 层面已达到可用状态，但与生产级产品仍有差距，核心差距在**数据积累**和**场景覆盖**。

## 七、方法论总结

### 7.1 本次研发验证的有效实践

1. **文档先行**：PRD → Tech Design → 开发 → 测试 → 复盘，流程清晰
2. **分层架构**：编排层统一调度，服务层职责分离
3. **受控 AI**：模型理解 + 规则约束，安全与智能兼顾
4. **测试驱动**：核心功能都有测试覆盖，重构有信心
5. **快速迭代**：小步快跑，及时调整方向

### 7.2 需要改进的实践

1. **需求确认**：增加需求评审环节，避免理解偏差
2. **代码审查**：引入代码 Review 机制，提升代码质量
3. **性能关注**：早期建立性能基准，避免后期返工
4. **数据准备**：知识库等数据应提前准备，不拖到最后

### 7.3 给未来项目的建议

| 阶段 | 建议 |
|------|------|
| 启动前 | 明确 Demo 边界，避免范围蔓延 |
| 设计阶段 | 关键交互用流程图确认，不依赖文字描述 |
| 开发阶段 | 核心链路先跑通，细节后优化 |
| 测试阶段 | 自动化测试覆盖主链路，人工测试关注体验 |
