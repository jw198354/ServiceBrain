# ServiceBrain 会话管理架构分析报告

## 1. 需求拆解

### 核心目标
分析 ServiceBrain 当前会话管理架构，对照商业化客服系统（Intercom、Zendesk、阿里小蜜等）识别差距并提出改进方案。

### 功能需求
- 单用户单会话模式（当前实现）
- 基于工作记忆的上下文管理
- 意图识别与槽位填充
- 退款/物流/售前等场景路由
- 工单兜底机制

### 非功能需求（对照商业化标准）
- 多会话并发支持
- 会话状态机与生命周期管理
- SLA 追踪与响应时效管理
- 跨渠道会话统一
- 会话标签与分析
- 人工无缝切换
- 高并发与水平扩展能力
- 完整的会话审计日志

### 约束条件
- 当前使用 SQLite 演示数据库
- 单 WebSocket 连接模式
- 匿名用户模型
- LangChain 用于 AI 编排

### 假设
- 目标是从 Demo 向商业化产品演进
- 需要支持多租户和企业级部署
- 需要考虑与现有 CRM/工单系统集成

### 待澄清问题
- 目标并发规模是多少？
- 是否需要支持多渠道（Web/App/微信/邮件）？
- 是否需要与现有客服系统（如 Zendesk）集成？
- 多租户隔离级别要求？

## 2. 当前架构分析

### 2.1 已实现的优势设计

| 优势 | 说明 | 价值 |
|------|------|------|
| **工作记忆 (Working Memory)** | `MemoryService.load_working_memory()` 加载最近对话 + 会话状态 | 支持上下文感知的对话 |
| **主题记忆 (Topic Memory)** | 按订单聚合的持久记忆 `TopicMemory` | 跨会话的订单级上下文 |
| **意图识别与槽位填充** | LLM 意图识别 + 规则补槽机制 | 结构化任务处理 |
| **漂移检测** | `classify_shift_type()` 检测主题/任务漂移 | 防止上下文混乱 |
| **上下文压缩** | `compress_context_if_needed()` 触发摘要生成 | 控制 token 消耗 |
| **工单兜底机制** | 连续失败/低置信度时触发工单 | 保证服务可用性 |
| **幂等设计** | ToolService 的幂等窗口控制 | 防止重复执行 |
| **Grounded LLM** | `_build_runtime_context()` 注入业务上下文 | 减少模型幻觉 |

### 2.2 架构问题与差距分析

按照严重程度分级：

#### Critical（严重问题）

| 问题 | 现状 | 风险 | 商业化对照 |
|------|------|------|-----------|
| **单会话模式** | 用户只能有一个 ACTIVE 会话，激活新会话时自动关闭旧会话 (`session_service.py:78-93`) | 无法支持用户同时处理多个问题（如同时咨询退款和物流） | Intercom/Zendesk 支持无限并发会话 |
| **会话状态过于简单** | 仅有 `creating/active/closed/error` 四种状态 (`session.py:9-13`) | 无法表达复杂服务流程（如等待用户回复、升级处理中、SLA 计时中） | 商业化系统有 10+ 状态（active/paused/pending/suspended/closed/escalated/sla_breached 等） |
| **WebSocket 连接与会话紧耦合** | `ws_routes.py` 中一个连接绑定一个 session_id | 无法支持多设备、多标签页同时在线 | 商业化系统支持连接 - 会话解耦，一个用户多连接聚合 |
| **无会话路由与分配机制** | 所有请求由同一个 OrchestratorService 处理 | 无法实现技能路由、负载均衡、VIP 优先等策略 | 阿里小蜜/Zendesk 有完整的路由引擎 |
| **SLA 管理缺失** | 无响应时间追踪、无超时升级 | 无法保证服务质量和合规性 | 商业化系统有 SLA 策略引擎和 breach 告警 |

#### High（高优先级问题）

| 问题 | 现状 | 风险 | 商业化对照 |
|------|------|------|-----------|
| **会话与连接强绑定** | `ws_routes.py` 中连接断开后会话状态不保留 | 用户断线重连后上下文丢失 | 商业化系统会话状态持久化，支持断点续聊 |
| **无会话标签体系** | 仅有简单的 topic/task 字段 | 无法进行分类统计、质量分析 | Zendesk 支持自定义标签和触发器 |
| **人工切换机制简陋** | 仅通过工单卡片引导 (`_ticket_card_response`) | 无法实现真正的机器人→人工无缝切换 | 商业化系统支持实时转接、协同会话 |
| **记忆系统无版本控制** | TopicMemory/SessionSummary 直接覆盖更新 | 无法追溯历史状态、无法审计 | 企业级系统需要完整的变更日志 |
| **无多渠道支持** | 仅 WebSocket 一种接入方式 | 无法整合 Web/App/微信/邮件等多渠道 | 全渠道客服是商业化基础能力 |

#### Medium（中优先级问题）

| 问题 | 现状 | 风险 | 商业化对照 |
|------|------|------|-----------|
| **匿名用户模型** | 仅有 AnonymousUser 模型 | 无法支持企业客户、VIP 识别、用户分群 | 商业化系统有完整的客户档案 |
| **会话历史查询简单** | `GET /session/{id}/messages` 无分页过滤 | 大数据量时性能问题 | 商业化系统有分页、搜索、过滤 |
| **无会话转移机制** | 无法在机器人之间、人机之间转移 | 复杂问题无法协作处理 | 支持会话转接、协同处理 |
| **监控与可观测性不足** | 仅有 print 日志 | 无法追踪会话质量、性能瓶颈 | 需要完整的指标、日志、告警 |
| **配置硬编码** | 阈值（如 10 条消息压缩）写死在代码中 | 无法动态调优 | 商业化系统有配置中心和 A/B 测试 |

## 3. 架构改进方案

### 方案 A：渐进式重构（推荐）

**核心思路**：在现有架构基础上增量改进，保持向后兼容，分阶段替换。

**架构拓扑**：
```
                    ┌─────────────────────────────────────────────────────────┐
                    │                   API Gateway / Load Balancer            │
                    └─────────────────────────────────────────────────────────┘
                                            │
         ┌──────────────────────────────────┼──────────────────────────────────┐
         │                                  │                                  │
         ▼                                  ▼                                  ▼
┌─────────────────┐              ┌─────────────────┐              ┌─────────────────┐
│  Channel Layer  │              │  Channel Layer  │              │  Channel Layer  │
│  (WebSocket)    │              │  (HTTP/REST)    │              │  (Third-party)  │
└─────────────────┘              └─────────────────┘              └─────────────────┘
         │                                  │                                  │
         └──────────────────────────────────┼──────────────────────────────────┘
                                            │
                                            ▼
                    ┌─────────────────────────────────────────────────────────┐
                    │              Session Management Gateway                  │
                    │  - 连接/会话解耦    - 多路复用    - 负载均衡            │
                    └─────────────────────────────────────────────────────────┘
                                            │
         ┌──────────────────────────────────┼──────────────────────────────────┐
         │                                  │                                  │
         ▼                                  ▼                                  ▼
┌─────────────────┐              ┌─────────────────┐              ┌─────────────────┐
│ Session Service │              │ Routing Service │              │  SLA Service    │
│ (重构后)        │              │ (新增)          │              │  (新增)         │
└─────────────────┘              └─────────────────┘              └─────────────────┘
         │                                  │
         └──────────────────────────────────┼──────────────────────────────────┘
                                            │
                                            ▼
                    ┌─────────────────────────────────────────────────────────┐
                    │              Orchestrator Service (保持)                 │
                    └─────────────────────────────────────────────────────────┘
```

**优势**：
- 保持现有 OrchestratorService 核心逻辑，降低重构风险
- 可以分阶段上线，每个阶段独立验证
- 团队学习曲线平缓

**劣势**：
- 需要维护过渡期的兼容性代码
- 部分历史债务无法彻底清理

**适用前提**：
- 团队规模有限（<10 人）
- 需要在 3 个月内看到明显改进
- 现有服务需要保持在线

---

### 方案 B：事件驱动架构（进取方案）

**核心思路**：引入事件总线，将所有会话行为事件化，实现完全解耦。

**架构拓扑**：
```
┌───────────────────────────────────────────────────────────────────────────┐
│                         Event Bus (Redis Stream / Kafka)                   │
└───────────────────────────────────────────────────────────────────────────┘
        │                │                │                │
        ▼                ▼                ▼                ▼
┌───────────────┐ ┌───────────────┐ ┌───────────────┐ ┌───────────────┐
│ Session       │ │ Conversation  │ │ Routing       │ │ Notification  │
│ Event Handler │ │ Event Handler │ │ Event Handler │ │ Event Handler │
└───────────────┘ └───────────────┘ └───────────────┘ └───────────────┘
        │                │                │                │
        └────────────────┴────────────────┴────────────────┘
                                         │
                                         ▼
                    ┌─────────────────────────────────────────┐
                    │         CQRS Read Model (查询)           │
                    │         - Session View                  │
                    │         - Conversation View             │
                    └─────────────────────────────────────────┘
```

**优势**：
- 完全解耦，便于水平扩展
- 支持事件溯源，完整的审计能力
- 便于集成第三方系统

**劣势**：
- 复杂度高，需要事件一致性保障
- 开发和运维成本显著增加
- 团队需要事件驱动架构经验

**适用前提**：
- 目标并发 > 10000 会话/秒
- 团队有事件驱动架构经验
- 有专门的运维团队

---

### 方案 C：混合架构（折中方案）

**核心思路**：核心会话管理采用同步架构，非核心能力（如摘要生成、数据分析）异步化。

**架构拓扑**：
```
┌─────────────────────────────────────────────────────────────────────────┐
│                         Sync Path (Hot Path)                             │
│  ┌─────────────┐    ┌─────────────┐    ┌─────────────┐                  │
│  │   Channel   │───▶│   Session   │───▶│   Chat      │                  │
│  │   Layer     │    │   Gateway   │    │   Engine    │                  │
│  └─────────────┘    └─────────────┘    └─────────────┘                  │
└─────────────────────────────────────────────────────────────────────────┘
                              │
                              │ (Async Events)
                              ▼
┌─────────────────────────────────────────────────────────────────────────┐
│                         Async Path (Cold Path)                           │
│  ┌─────────────┐    ┌─────────────┐    ┌─────────────┐                  │
│  │  Context    │    │   SLA       │    │   Analytics │                  │
│  │  Compressor │    │   Tracker   │    │   Engine    │                  │
│  └─────────────┘    └─────────────┘    └─────────────┘                  │
└─────────────────────────────────────────────────────────────────────────┘
```

**优势**：
- 核心链路保持简单可控
- 非核心能力异步化提升性能
- 复杂度介于方案 A 和 B 之间

**劣势**：
- 需要区分冷热路径，设计复杂
- 异步任务需要额外监控

---

### 推荐方案：方案 A（渐进式重构）

**推荐理由**：

| 评估维度 | 方案 A | 方案 B | 方案 C |
|---------|-------|-------|-------|
| 实施风险 | 低 | 高 | 中 |
| 团队学习成本 | 低 | 高 | 中 |
| 上线速度 | 快（可分阶段） | 慢 | 中 |
| 长期扩展性 | 中 | 高 | 中高 |
| 维护成本 | 中 | 高 | 中 |

**决策依据**：
1. ServiceBrain 处于从 Demo 向产品演进的早期阶段
2. 团队规模有限，需要快速验证核心价值
3. 现有 OrchestratorService 的核心逻辑（意图识别、槽位填充、漂移检测）设计良好，应保留
4. 优先解决 Critical 问题（单会话模式、状态机、路由），后续可继续演进

## 4. 模块边界设计

### 重构后的模块边界

| 模块 | 核心职责 | 对外接口/事件 | 数据所有权 | 说明 |
|------|----------|---------------|------------|------|
| **Session Gateway** | 连接管理、会话路由、负载均衡 | `connect()`, `route()`, `close()` | 无状态 | 新增模块，解耦连接与会话 |
| **Session Service** | 会话生命周期、状态机 | `create()`, `transition()`, `get_status()` | `sessions` 表 | 重构现有服务，增加状态 |
| **Conversation Service** | 对话上下文、消息聚合 | `load_context()`, `append_message()` | `messages`, `memories` 表 | 从 MemoryService 拆分 |
| **Routing Service** | 技能路由、分配策略 | `route_to_agent()`, `get_queue_status()` | `routing_rules` 表 | 新增模块 |
| **SLA Service** | 响应时效追踪、升级策略 | `start_timer()`, `check_breach()`, `escalate()` | `sla_policies`, `breach_logs` 表 | 新增模块 |
| **Channel Adapter** | 多渠道适配（WS/HTTP/第三方） | `receive()`, `send()`, `transform()` | 无状态 | 新增模块 |
| **Orchestrator Service** | 对话编排、意图识别、工具路由 | `process_message()` | 无状态 | 保持现有，简化会话管理职责 |
| **Memory Service** | 长期记忆、摘要生成 | `get_topic_memory()`, `compress_context()` | `topic_memories`, `summaries` 表 | 简化，专注长期记忆 |

### 模块依赖关系

```
Session Gateway ──▶ Session Service ──▶ Conversation Service
       │                                      │
       │                                      ▼
       │                               Orchestrator Service
       │                                      │
       ▼                                      ▼
Routing Service ◀───────────────────── Memory Service
       │
       ▼
   SLA Service
```

## 5. 核心流程设计

### 5.1 会话生命周期状态机

```
                    ┌──────────────┐
                    │   CREATED    │
                    └──────┬───────┘
                           │ activate()
                           ▼
        ┌──────────────┐  pending  ┌──────────────┐
        │   PAUSED     │◀─────────▶│    ACTIVE    │
        └──────┬───────┘           └──────┬───────┘
               │                          │
               │ close()                  │ escalate()
               ▼                          ▼
        ┌──────────────┐           ┌──────────────┐
        │    CLOSED    │           │  ESCALATED   │
        └──────────────┘           └──────┬───────┘
                                          │
                                          │ resolve()
                                          ▼
                                   ┌──────────────┐
                                   │    CLOSED    │
                                   └──────────────┘
```

### 5.2 多会话并发流程

```
用户接入 ──▶ Session Gateway
               │
               ├──▶ 检查用户现有会话
               │      │
               │      ├── 无活跃会话 ──▶ 创建新会话
               │      │
               │      ├── 单活跃会话 ──▶ 询问：继续当前会话 or 开启新话题？
               │      │
               │      └── 多活跃会话 ──▶ 展示会话列表供选择
               │
               └──▶ 路由到对应会话实例
```

### 5.3 人机无缝切换流程

```
机器人处理中
     │
     ├── 检测到无法处理 ──▶ 触发转人工规则
     │                        │
     │                        ├── 检查人工坐席可用性
     │                        │
     │                        ├── 将会话状态转为 ESCALATED
     │                        │
     │                        ├── 通知坐席（WebSocket 推送）
     │                        │
     │                        └── 坐席接入，继续对话
     │
     └── 坐席处理完成 ──▶ 会话关闭，生成摘要
```

### 5.4 一致性策略

| 场景 | 一致性要求 | 策略 |
|------|-----------|------|
| 会话状态变更 | 强一致 | 数据库事务 + 乐观锁 |
| 消息写入 | 最终一致 | 异步写入 + 重试 |
| 记忆更新 | 最终一致 | 事件触发 + 幂等处理 |
| SLA 计时 | 最终一致 | 定时任务补偿 |

### 5.5 降级/回滚策略

| 故障场景 | 降级策略 | 回滚方案 |
|---------|---------|---------|
| Session Gateway 故障 | 切换到备用实例 | DNS 切换 |
| Routing Service 故障 | 默认路由到通用队列 | 配置热切换 |
| SLA Service 故障 | 暂停 SLA 追踪，记录日志 | 事后补偿计算 |
| Orchestrator 故障 | 返回标准错误响应 | 请求重试（幂等） |

## 6. 实施计划

### Phase 1: 基础加固（1-2 周）

**目标**：解决 Critical 问题中的单会话模式和状态机缺陷。

**交付物**：
- [ ] 扩展 SessionStatus 枚举（增加 `paused`, `escalated`, `pending_user`）
- [ ] 修改 `activate_session()` 逻辑，支持多会话并发
- [ ] 增加会话选择 API（`GET /user/sessions` 列出活跃会话）
- [ ] 会话状态变更日志表 (`session_status_logs`)

**依赖**：无外部依赖

**验收标准**：
- 用户可以同时拥有多个 ACTIVE 会话
- 前端可以展示并切换会话
- 状态变更有完整审计日志

**风险**：
- 前端需要适配多会话选择 UI
- 现有测试需要更新

---

### Phase 2: 核心能力（2-4 周）

**目标**：实现会话路由、SLA 管理、连接 - 会话解耦。

**交付物**：
- [ ] Session Gateway 模块（连接管理、会话路由）
- [ ] Routing Service（技能路由、队列管理）
- [ ] SLA Service（时效追踪、升级策略）
- [ ] WebSocket 连接池管理
- [ ] 会话分配策略配置表

**依赖**：Phase 1 完成

**验收标准**：
- 支持基于技能的会话路由
- SLA breach 能触发告警/升级
- 支持断线重连后会话恢复

**风险**：
- 路由策略需要业务配置
- SLA 阈值需要调优

---

### Phase 3: 高级特性（1-2 月）

**目标**：实现多渠道支持、人机协作、分析能力。

**交付物**：
- [ ] Channel Adapter（HTTP/第三方渠道）
- [ ] 人工坐席 WebSocket 接口
- [ ] 会话标签系统
- [ ] 会话分析报表
- [ ] 会话转移 API

**依赖**：Phase 2 完成

**验收标准**：
- 支持至少一种第三方渠道接入
- 坐席可以无缝接入机器人会话
- 可以按标签筛选和统计会话

**风险**：
- 第三方渠道对接复杂度不确定
- 坐席端 UI 开发工作量

## 7. 关键决策记录（ADR）

### ADR-001: 采用渐进式重构而非重写

**背景**
需要在 3 个月内将会话管理能力提升到商业化水平，同时保持现有服务可用。

**决策**
采用方案 A（渐进式重构），在现有架构基础上增量改进。

**后果**

**积极影响**
- 保持现有 OrchestratorService 核心能力
- 分阶段上线，降低风险
- 团队可以在实践中学习

**消极影响**
- 需要维护过渡期兼容性代码
- 部分历史债务（如模型命名）无法彻底清理

**备选方案**
- 方案 B（事件驱动）：复杂度过高，不适合当前阶段
- 方案 C（混合）：可以作为 Phase 2 的演进方向

---

### ADR-002: 会话状态机扩展

**背景**
当前仅有 4 种状态，无法表达复杂服务流程。

**决策**
扩展 SessionStatus 为：
```python
class SessionStatus(str, enum.Enum):
    CREATED = "created"
    ACTIVE = "active"
    PAUSED = "paused"              # 等待用户回复
    PENDING_USER = "pending_user"  # 等待用户补充信息
    ESCALATED = "escalated"        # 已升级人工
    PENDING_AGENT = "pending_agent" # 等待坐席接入
    CLOSED = "closed"
    ERROR = "error"
```

**后果**
- 状态流转需要明确的业务规则
- 需要状态变更日志用于审计

### ADR-003: 连接 - 会话解耦设计

**背景**
当前 WebSocket 连接与 session_id 绑定，无法支持多设备。

**决策**
引入 ConnectionSession 模型：
```python
class ConnectionSession(Base):
    connection_id: str       # WebSocket 连接 ID
    user_id: str             # 用户 ID
    session_id: str          # 会话 ID（可变更）
    status: str              # connected/disconnected
```

**后果**
- 需要修改 ws_routes.py 的连接处理逻辑
- 支持一个用户多个连接聚合到同一会话
